# RFE-5280: Minimum Viable X.509 Certificate Profile

**Status:** Evidence-derived profile of [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280).
**Derived from:** 21,536 real-world certificates (Certificate Transparency log
`ct.googleapis.com/logs/us1/argon2026h1`, from index 0), seed `0`, prune
threshold `0.001`. Reproducible — see [§9](#9-provenance-and-reproducibility).

This document is an **original profile** of RFC 5280. It does not reproduce or
modify RFC 5280's text; it defines a narrower certificate syntax and records, in
[§6](#6-deltas-from-rfc-5280-normative), how and why it differs. RFC 5280 (and
the underlying X.509 / X.520 / PKIX specifications) remains authoritative for the
certificate semantics — signature verification, path validation, extension
processing — that this profile does not restate.

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as described
in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). Syntax is ASN.1, encoded
with DER per [X.690](https://www.itu.int/rec/T-REC-X.690).

## 1. Abstract

RFC 5280 profiles a certificate structure that still admits fields and encodings
which current Web PKI does not produce. A profile that a certificate parser must
accept can be smaller than what the grammar permits. RFE-5280 is that profile: an
X.509 certificate syntax in which **every production is present because
real-world certificates exercised it**, or because it is load-bearing for
security or interoperability and is explicitly protected. Encodings and fields
that RFC 5280 permits but the measured corpus did not use are **not part of this
profile**, and a conforming implementation MUST reject them.

## 2. Introduction

A certificate parser is a high-value attack surface: it runs before trust is
established, on adversary-supplied bytes. RFC 5280 carries structure for
backward compatibility — the v2 unique identifiers, the full X.520 set of
directory-string encodings — that modern certificates do not use. Every unused
production is code that must be carried and an input that can be probed.

RFE-5280 narrows the certificate grammar to observed practice, with one
deliberate exception: a small set of security- and interoperability-critical
productions is retained even at zero measured frequency (see
[§7](#7-criticality-overrides)), because their absence would be a vulnerability
rather than a simplification.

## 3. Notational conventions

The syntax below is the normative ASN.1 module of this profile, generated

## 4. Normative syntax

A conforming certificate MUST match the `Certificate` production and MUST NOT
exercise any production outside this module.

```asn1
-- Minified MVS grammar for rfc5280-x509 (generated).
-- 16 nodes pruned below usage threshold 0.001.

rfc5280_x509 DEFINITIONS ::= BEGIN

Certificate ::= SEQUENCE { tbsCertificate TBSCertificate, signatureAlgorithm AlgorithmIdentifier, signatureValue BIT STRING }
TBSCertificate ::= SEQUENCE { version [0] EXPLICIT Version OPTIONAL, serialNumber CertificateSerialNumber, signature AlgorithmIdentifier, issuer Name, validity Validity, subject Name, subjectPublicKeyInfo SubjectPublicKeyInfo, extensions [3] EXPLICIT Extensions OPTIONAL }
Version ::= INTEGER
CertificateSerialNumber ::= INTEGER
AlgorithmIdentifier ::= SEQUENCE { algorithm OBJECT IDENTIFIER, parameters ANY OPTIONAL }
Name ::= CHOICE { rdnSequence RDNSequence }
RDNSequence ::= SEQUENCE OF RelativeDistinguishedName
RelativeDistinguishedName ::= SET OF AttributeTypeAndValue
AttributeTypeAndValue ::= SEQUENCE { type AttributeType, value AttributeValue }
AttributeType ::= OBJECT IDENTIFIER
AttributeValue ::= DirectoryString
DirectoryString ::= CHOICE { printableString PrintableString, utf8String UTF8String }
Validity ::= SEQUENCE { notBefore Time, notAfter Time }
Time ::= CHOICE { utcTime UTCTime, generalTime GeneralizedTime }
SubjectPublicKeyInfo ::= SEQUENCE { algorithm AlgorithmIdentifier, subjectPublicKey BIT STRING }
Extensions ::= SEQUENCE OF Extension
Extension ::= SEQUENCE { extnID OBJECT IDENTIFIER, critical BOOLEAN OPTIONAL, extnValue OCTET STRING }

END
```

## 5. Components

- **`TBSCertificate`** — the signed body. `version` and `extensions` are present
  (all sampled certificates were v3 with extensions). The v2 unique-identifier
  fields are excluded ([§6.2](#62-v2-unique-identifiers)).
- **`Name` / `DirectoryString`** — distinguished names as `AttributeTypeAndValue`
  sequences. String values are `printableString` or `utf8String` only
  ([§6.1](#61-directorystring-encodings)).
- **`Validity` / `Time`** — `notBefore` / `notAfter`, each `utcTime` or
  `generalTime`. `generalTime` is retained under the override floor
  ([§7](#7-criticality-overrides)).
- **`Extensions` / `Extension`** — `extnID`, an optional `critical` flag (retained;
  [§7](#7-criticality-overrides)), and an opaque `extnValue`. Extension *values*
  are not modeled by this profile; a verifier processes them per RFC 5280.
- **`SubjectPublicKeyInfo`**, **`AlgorithmIdentifier`**, serial number, and
  signature are as in RFC 5280.

## 6. Deltas from RFC 5280 (normative)

A conforming implementation MUST reject a certificate that relies on an excluded
production.

### 6.1 DirectoryString encodings

X.520 / RFC 5280 permit `DirectoryString ::= CHOICE { teletexString,
printableString, universalString, utf8String, bmpString }`. RFE-5280 keeps only:

```asn1
DirectoryString ::= CHOICE { printableString PrintableString, utf8String UTF8String }
```

In 21,536 certificates, `printableString` occurred in 100% and `utf8String` in
68%; `teletexString`, `universalString`, and `bmpString` occurred **zero** times
and are excluded. These legacy encodings are a historically attack-prone source
of name-comparison ambiguity; rejecting them narrows the surface with no observed
loss.

### 6.2 v2 unique identifiers

RFC 5280 retains the v2 `issuerUniqueID` (`[1] IMPLICIT`) and `subjectUniqueID`
(`[2] IMPLICIT`) fields in `TBSCertificate`. RFC 5280 §4.1.2.8 states that
conforming CAs SHOULD NOT generate them, and none in the corpus did — they are
**excluded**. A certificate carrying either field is rejected.

## 7. Criticality overrides

Retained regardless of measured frequency because omission would be a security or
interoperability defect. Recorded, with justification and owner, in the
Criticality Override Registry
([`overrides.yaml`](../../pipeline/mvs_pipeline/overrides.yaml)).

| Production | Rationale |
| --- | --- |
| `Extension` `critical` BOOLEAN | Gates unknown-critical-extension rejection (RFC 5280 §4.2). Encoded only when TRUE; a verifier that cannot parse it cannot enforce criticality. |
| `Time` `generalTime` / GeneralizedTime | Mandatory for validity dates ≥ 2050 (RFC 5280 §4.1.2.5); used by long-lived roots/CAs, **zero** occurrences among current leaf certificates. Dropping it would reject valid CA certificates. |
| `DirectoryString` `printableString` | The standard encoding for country and much legacy DN naming across the installed base; protected against a sample skewed to UTF8String. |

## 8. Security considerations

- **Strict rejection, no degradation.** A conforming implementation MUST reject a
  non-conforming certificate outright and MUST NOT fall back to the broader RFC
  5280 grammar. The reference implementation fails with a specific
  `ERR_MVS_UNSUPPORTED_NODE` naming the excluded production.
- **Criticality.** The `critical` flag is retained so a verifier can enforce the
  RFC 5280 §4.2 rule that an unrecognized critical extension MUST cause rejection.
  This profile models extension *presence and criticality*, not extension values;
  value processing remains the verifier's responsibility under RFC 5280.
- **Name encodings.** Restricting `DirectoryString` to `printableString` /
  `utf8String` removes deprecated encodings associated with name-comparison
  confusion.
- **Bounds.** An implementation SHOULD enforce a maximum DER size and nesting
  depth and reject inputs that exceed them before full decoding; the reference
  implementation defaults to 64 KiB / depth 1024 for certificates.

## 9. Conformance

An implementation conforms to RFE-5280 if, for every input, it accepts the input
**iff** the input matches the `Certificate` production in
[§4](#4-normative-syntax) without exercising any production excluded by
[§6](#6-deltas-from-rfc-5280-normative). The native reference parser
(`mvs-refparse`, `MvsCertParser`) and the `mvs-validate --der` tool are the
executable definition of this behavior.

## 10. Provenance and reproducibility

The module in [§4](#4-normative-syntax) is not authored by hand; it is the
mechanical result of measuring usage and pruning. A CT log is append-only, so a
fixed `(log, start index, seed)` reproduces the same corpus and therefore this
grammar. The provenance is recorded alongside
[`pruned.json`](pruned.json) and the fetch's `provenance.json`; collection and
regeneration commands are in [`README.md`](README.md) and
[`docs/telemetry.md`](../../docs/telemetry.md).
